# Data model — Tahona.BakeryPOS MVP v1.1

Status: **proposal for review** (PostgreSQL, I-18).

## Conventions

| Topic | Rule |
|---|---|
| Names | `snake_case`, plural tables, one schema per module (`org`, `sec`, `cat`, `inv`, `cash`, `sales`, `pay`, `fis`, `aud`, `int`). All identifiers are English |
| Primary key | `id uuid` (UUID v7 generated by the application) |
| Multi-company | `company_id` NOT NULL on every business table, first column of the indexes; composite FKs `(company_id, x_id)` on critical relationships |
| Money | `decimal(18,2)`; rates `decimal(7,4)`; quantities `decimal(18,4)` |
| Dates | `timestamptz(3)` in UTC |
| Concurrency | `row_version bytea` on editable tables (renewed by the application on every change) |
| Audit | `created_at/by`, `modified_at/by`; soft delete (`deleted_at/by`) only on master data |
| States | `varchar` + `CHECK`; one state per concept (sale ≠ payment ≠ inventory ≠ document) |
| Idempotency | `idempotency_key`/`external_id` columns with a filtered **unique** index |
| Stored codes | English: permissions (`sales.void`), system roles (`OWNER`, `BRANCH_MANAGER`, `CASHIER`), default reasons and payment methods (`WASTE`, `CASH`, `TRANSFER`…), audit actions (`create`, `update`, `delete`). Seeded display names stay Spanish because users see them |

## Key integrity rules

1. A `confirmed` sale has `payment_status = paid`, `inventory_status = applied` and Σ approved payments = total (+ cash change).
2. A payment attempt only moves forward: `created → pending → {approved, declined, voided, error, expired}`; `unknown` only leaves through a provider query.
3. Inventory balance = Σ movements (verifiable with the reconciliation); it is never updated without a movement.
4. An `unknown` fiscal document is not resent without a recorded status query.
5. Every business FK points to rows of the same `company_id` (validated in the application and with composite FKs on sales, payments, inventory and documents).
6. Voids and returns never delete rows: they create compensating movements/documents.

initial migration (there is no production data). An optional script can import catalog and users from the demo
