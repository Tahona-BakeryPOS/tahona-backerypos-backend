Short ADR-style format. **Blocking** = the affected phase does not start without an answer.

## Approved (27/10/2026)

D-01 (new database with a clean initial migration), D-02 (.NET 10 LTS; the SQL Server 2022 engine was
replaced by PostgreSQL, see I-18), D-13 (two repos + `docs/`), D-14 (modules by folder + architecture
tests), D-16 (dependencies on the list; Testcontainers with PostgreSQL instead of SQL Server).
When starting phase 2: D-08 (a user in several companies through memberships) and D-09 (company onboarding only
by the platform administrator). When starting phase 3: D-07 (list prices **with VAT included**, stored
per price in `includes_tax`) and advancing phase by phase with the previous system's screens. When starting phase 4:
D-06 (insufficient stock **configurable per product**: `allow` permits a negative balance, `block` prevents it
unless a supervisor authorizes with a PIN, which is audited). When starting phase 5: D-12 (**block the cash close**
while there are unresolved pending payments). When starting phase 6: D-03 (**Bold**, card-terminal API: card, Nequi and Bold QR
charged on the terminal from the POS) and, since Bold only reports the result by webhook, an **audited manual
approval** of a payment whose webhook did not arrive (an exception to "a payment is only approved by the backend"; see I-23). When
starting phase 7: D-04 (**Siigo**), D-05 (**electronic invoice on every sale**, with the customer's data or as a
final consumer; **later replaced by D-17, which makes it optional per company**. Siigo does not offer the electronic POS equivalent document and the DIAN allows replacing it; **confirm with
the accountant**) and D-15 (**retain for 5 years**, configurable; confirm with the accountant). When starting phase 9: D-11 (**a full void only while the sale's shift is still open** and with no previous returns, with an automatic credit note if the invoice was already accepted; after the close, only a return; a supervisor authorizes the return on the spot with their PIN; the money is **always returned in cash** from the open register, also if it was paid on the terminal, because Bold does not refund by API; per line it is chosen whether the product goes back into inventory; **validate with the accountant**; see I-26). When starting phase 10: D-10 (**one VPS per environment with Docker Compose**: PostgreSQL, API, migrations bundle and Caddy as the API's HTTPS proxy; staging and production prepared, not deployed; see I-27 and `runbooks.md`).

## Taken while implementing phase 1 (for review)

| Id | Decision | Reason |
|---|---|---|
| I-01 | **A single `DbContext`** (`AppDbContext`) with one SQL schema per module, instead of one context per module as `architecture.md` said | Confirming a sale touches sales, payments, inventory, cash, fiscal document and outbox: with one context it is a single transaction with no distributed coordination. The boundaries between modules are enforced by the architecture tests |
| I-02 | OpenAPI with `Microsoft.AspNetCore.OpenApi` (native in .NET 10) instead of Swashbuckle | An official Microsoft package; Swashbuckle 6.x is not designed for .NET 10. No Swagger UI for now (the document is at `/openapi/v1.json`) |
| I-03 | EF Core 10 **named** query filters (`Tenant`, `SoftDelete`) | Allows turning off only the soft delete without ever turning off company isolation |
| I-04 | ~~Development with LocalDB~~ — replaced by I-18 (Postgres in a container) | — |
| I-05 | The project has its own `UserSecretsId` | It shared the previous system's and inherited its PostgreSQL connection string |
| I-06 | ~~`System.Security.Cryptography.Pkcs` pinned~~ — no longer applies: it came from `Microsoft.Data.SqlClient`, which left with I-18. Instead `Microsoft.EntityFrameworkCore.Relational` 10.0.14 is pinned (Npgsql 10.0.3 brings 10.0.4 and clashes with EF Core 10.0.14) | — |
| I-07 | Business-rule failures are also stored in the idempotency table (4xx); 5xx and exceptions release the key | Same retry → same response; a transient failure allows retrying |

## Taken while implementing phase 2 (for review)

| Id | Decision | Reason |
|---|---|---|
| I-08 | The `cash.cash_registers` table (only the register records) enters in phase 2; sessions and movements stay in phase 5 | Devices and PIN sign-in are tied to a register |
| I-09 | **Opaque** device token (256 bits, its SHA-256 is stored) in the `X-Device-Token` header; pairing codes of 8 characters, 15 min, single use, also stored as a hash | Revocable by deactivating the device, without depending on a JWT's expiry |
| I-10 | System roles per company: **Owner** (all company permissions, code `OWNER`), **Branch manager** (`BRANCH_MANAGER`) and **Cashier** (`CASHIER`; the previous system's). Assumed matrix in `DefaultRoles` | The exact permissions of each role still need confirming with the owner/accountant |
| I-11 | Rotating 14-day refresh token stored as a hash; reusing an already-rotated one revokes all the user's sessions. 60-min access token; 12 h register session with no refresh | Detecting refresh-token theft (OWASP) |
| I-12 | Lockout: 5 failed attempts → 5 min, the same for password (per user) and PIN (per membership). Also a limit of 10 requests/min per IP on the anonymous endpoints (429) | US-2.4; the per-IP limit slows brute force against several users |
| I-13 | Master-data `PUT` **requires** `If-Match` (428 `VERSION_REQUIRED` if missing, 412 `VERSION_CONFLICT` if it changed); `VERSION_CONFLICT` moves from 409 to 412 as the contract says | Avoid silent overwrites |
| I-14 | Company and user creation **without** `Idempotency-Key`: the response carries the one-time password and the idempotency table would store it in clear text. A retry collides with a duplicate NIT/email | Do not persist secrets |
| I-15 | Endpoints added to the contract: `POST /auth/change-password`, `POST /auth/logout`, `GET /device/users` (list for "tap your name", US-2.4). New codes: `USER_LOCKED` (423), `PASSWORD_CHANGE_REQUIRED`, `DUPLICATE_NIT`, `EMAIL_IN_USE`, `DUPLICATE_ASSIGNMENT`, `LAST_OWNER`, `SHARED_USER`, `SELF_DEACTIVATION`, `VERSION_REQUIRED` | Needed for the phase 2 flows |
| I-16 | Tax regime and responsibilities validated against the DIAN technical annex codes (regime 48/49; O-13, O-15, O-23, O-47, R-99-PN) | Mandatory onboarding data (US-1.1); verify the list with the accountant before phase 7 |
| I-18 | **PostgreSQL 17 as the only engine** (the owner's request, 27/10/2026; replaces SQL Server from D-01/D-02). Connection string in `ConnectionStrings:DefaultConnection`; dev Postgres in a container (base compose + override, `-p`, `--env-file .env.dev`, port 15432). A single initial migration (`InitialPostgreSql`). `bytea` row version renewed by the application, `timestamptz` UTC dates, outbox with `FOR UPDATE SKIP LOCKED`. Dependencies: `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 and `Testcontainers.PostgreSql` 4.16.0 (tests only); `Microsoft.EntityFrameworkCore.SqlServer` and `Testcontainers.MsSql` go away | Same engine and way of working as the previous system. Review D-10 (hosting): Azure SQL no longer applies; equivalent option: Azure Database for PostgreSQL |
| I-20 | Phase 3 (catalog): default taxes when creating a company: VAT 19 %, VAT 5 %, VAT 0 % (exempt), Excluded (no tax) and Consumption tax 8 %, plus the "General" category (it fulfils the part of I-17 that depended on the catalog). A tax's rate is not edited: another is created and the previous one is deactivated. Global units seeded: UND, KG, G, LB, L, ML with their UN/ECE code (94, KGM, GRM, LBR, LTR, MLT). A new price cannot start in the past or before the last validity; it opens its validity period and closes the open one. Product creation accepts an initial base price. `branch_products` uses `id` as PK with a unique index (branch_id, product_id) instead of a composite PK, like the other tables | Rates and DIAN codes to be confirmed with the accountant before phase 7; past validity periods would change the price of sales already made |
| I-21 | Phase 4 (inventory): default adjustment reasons (Daily production, Purchase or receipt, Waste, Damage or expiry, Internal use, Physical count, Correction) and a "Mostrador" location per branch, created when onboarding a company/branch and back-filled by the migration for existing ones. Default policy of a new product: `allow`. Adjustments, initial stock and counts are authorized by whoever records them (they hold `inventory.adjust`), so they can leave a negative balance; PIN authorization to sell without stock arrives with the sale (phase 8), where `InventoryLedger` already applies it. Balance concurrency with a row version (optimistic) instead of `FOR UPDATE`: two registers moving the same balance at once → the second fails and retries. No nightly reconciliation job yet: an on-demand query. `stock_balances` uses `id` as PK with a unique index (location_id, product_id) | Same pattern as I-20; automatic retry and the job are closed in phases 8 and 10 |
| I-22 | Phase 5 (cash): the expected amount is the signed sum of the session's movements (the opening is also an `opening` movement); default cash reasons from the previous system (Extra change, Owner contribution, Supplier payment, Safety withdrawal, Minor expenses), created when onboarding the company and back-filled by the migration. A withdrawal is authorized by whoever holds `cash.withdrawal` by sending their own token (in the POS: they choose their name and enter their PIN) and is stored as `authorized_by`. The session goes from `open` to `closed` (the `closing` state stays reserved). The D-12 block queries `IPendingPaymentsProbe`; until phase 6 its implementation returns 0 (there are no payments). The POS only shows Cash: Sale, Sales and the previous system's offline mode are removed from the navigation until phase 8 | An expected amount verifiable from the movement ledger; do not invent payments before their module |
| I-23 | Phase 6 (payments, Bold): with no status query or remote cancellation in the card-terminal API, there is no recovery worker; attempts with no response stay `pending`/`unknown` and are resolved by hand by whoever holds the new `payments.resolve` permission (Owner and Branch manager): approved with an approval number (marked as manual and audited), declined or cancelled. Credentials per company and environment encrypted with ASP.NET Core Data Protection (in production the Data Protection keys must be persisted outside the server, phase 10). Each register's terminal is configured in `pay.register_terminals` (model and serial; a new table relative to `data-model.md`). For the sandbox acceptance test, while there are no sales (phase 8), there is a test charge without a sale (`purpose = test`). Default methods: Cash, Card (Bold terminal), Nequi (Bold), Bold QR and Transfer (manual with a reference) | Required by Bold's verified API; see `payment-integration.md` §11 |
| I-24 | Phase 7 (Siigo): numbering and resolutions in Siigo (the prefix and number returned are stored); products created in Siigo with their SKU the first time they are invoiced; taxes and payment methods paired with Siigo's in the configuration; configurable final consumer (`222222222222`); sending through the outbox with `Idempotency-Key` = the document id in base 36 (repeating it works as a status query); no XML by API (it stays in Siigo Nube), the CUFE is stored and the PDF is downloaded from Siigo; retention 5 years (D-15). While there are no sales (phase 8), issuing is triggered by the sale through `IFiscalDocumentIssuer` | Required by Siigo's verified API; see `electronic-invoicing.md` §9 |
| I-17 | Default payment methods, taxes and inventory location are **not** created at onboarding yet; they are added when their modules exist (phases 3, 4 and 6). Company logo pending (requires file storage) | Their tables do not exist yet |
| I-25 | Phase 8 (integrated sale): the sale stores four separate states (sale, payment, inventory, fiscal); it is confirmed when the approved payments cover the total and there are no pending payments; at that point it takes its number (per-company counter), deducts inventory, records the cash received and the change in the register and enqueues the invoice. Without active invoicing the sale stays `fiscal_status = not_required`. The customer's identification is stored on the sale (`customer_identification`, 4–15 digits) instead of the `parties` table, which is left for when there are customers with complete data. Quantities with at most 2 decimals (a Siigo limit). D-06: if a product with the `authorize` policy lacks stock, the payment answers `INSUFFICIENT_STOCK` and the sale is authorized by whoever holds `inventory.adjust` with their own token (PIN in the POS); it is stored in `stock_authorized_by`. A per-line discount only with the new `sales.discount` permission and with a reason; authorizing the discount by another user is pending. The result of the webhook or of the manual resolution reaches the sale through the outbox (`sales.payment-resolved`). The POS does not sell offline: the local queue, synchronization and the previous system's void were removed (the void returns in phase 9, D-11) | A persistent sale process with auditable states; no customer data that is not yet requested |
| I-26 | Phase 9 (voids, returns, reports): a return is completed in the same transaction (a single `completed` state; no deferred request and approval) and stores who authorized it (`approved_by`), not who asked for it. The value returned per line is proportional to the line total and the last one returns the exact remainder. Cash is validated against the register's expected amount (`WITHDRAWAL_EXCEEDS_BALANCE`). Refunds (`pay.refunds`) are spread across the sale's approved payments, from the last to the first, and only in cash. A return's credit note carries DIAN reason 1, price with VAT and a proportional discount; it waits in the outbox while the invoice is not accepted and is left void if the invoice was rejected. The report groups by Colombian days (UTC−5) and by confirmation date; sold excludes voided and net = sold − returned. A return of a sale from another shift is looked up by number in the POS (`GET /sales?number=`) | D-11; Siigo: `taxed_price` and `discount` on credit notes to verify in the test environment |
| I-27 | Phase 10 (deployment and tests): files in `deploy/` (compose, Caddyfile, `.env.deploy.example`, deployment, backup, restore and first-administrator scripts); Caddy is only the API's HTTPS proxy (`API_DOMAIN`): no client is built or served from this repo, and the web client's origin is declared with `CORS_ALLOWED_ORIGIN`. Images are built on the VPS from this repo (no container registry yet). Outside development the API requires `DataProtection:KeysPath` (a volume with backup, next to the database) and trusts `X-Forwarded-*` only with `ReverseProxy:Enabled`. The first platform administrator is created with `dotnet Tahona.BakeryPOS.Api.dll bootstrap-admin` (only if there is none). Load testing with k6 (a script, not a package) | Reproducible, cheap deployment for a few branches; the tests do not touch production |
| I-28 | English standardization (A-06): migration `EnglishCodes` moves the stored codes to English without losing data. Permissions (20): `sales.void`, `inventory.adjust`, `payments.resolve`, `returns.approve`, … (a permission id is derived from its code, so the migration inserts the new rows, re-points `sec.role_permissions` and deletes the old rows). System roles: `PROPIETARIO/ADMIN_SUCURSAL/CAJERO` → `OWNER/BRANCH_MANAGER/CASHIER`. Default adjustment reasons: `PRODUCCION/COMPRA/MERMA/DANO/CONSUMO/CONTEO/CORRECCION` → `PRODUCTION/PURCHASE/WASTE/DAMAGE/INTERNAL_USE/PHYSICAL_COUNT/CORRECTION`. Payment methods: `EFECTIVO/BOLD_TARJETA/TRANSFERENCIA` → `CASH/BOLD_CARD/TRANSFER`. Default stock location `MOSTRADOR` → `COUNTER`; tax `EXCLUIDO` → `EXCLUDED`. Audit actions `creacion/modificacion/eliminacion` → `create/update/delete`. Display names (shown to users) stay Spanish. Tokens issued before the change carry the old permission codes and stop working until the next sign-in/refresh. It is reversible (`Down`) | A single technical language; the API surface (routes, error codes) is unchanged so clients do not break |
| I-29 | API routes in English: every route path and query parameter was renamed (e.g. `/ventas` → `/sales`, `/sucursales` → `/branches`, `/cajas` → `/cash-registers`, `/sesiones-caja` → `/cash-sessions`, `/medios-pago` → `/payment-methods`, `/documentos-fiscales` → `/fiscal-documents`, `/plataforma/empresas` → `/platform/companies`, `/auth/cambiar-contrasena` → `/auth/change-password`; `sucursalId`/`desde`/`hasta`/`estado`/`buscar` → `branchId`/`from`/`to`/`status`/`search`). Renamed in place, keeping `/api/v1`, because nothing was in production and no client needed a transition. Error codes and error body keys followed in I-30 | One language across the codebase and the API contract; the full route list is in `api-contracts.md` |
| I-30 | The rest of the technical surface in English, since the product was not in production and had no clients to protect: error codes (`NO_ENCONTRADO` → `NOT_FOUND`, `EXISTENCIAS_INSUFICIENTES` → `INSUFFICIENT_STOCK`, `CAJA_CERRADA` → `CASH_SESSION_CLOSED`, `VALIDACION` → `VALIDATION`…) and the C# `Error` members that carry them; the error body keys (`codigo/mensaje/detalles` → `code/message/details`); the web client's browser routes (`/vincular` → `/pair-device`, `/backoffice/ingresar` → `/backoffice/sign-in`, `ventas/pagos` → `sales/payments`…) and its feature folders; logs, startup errors and operator console messages; test names. The `message` texts shown to users and the seeded display names stay Spanish | One technical language everywhere; only what users read is Spanish |
